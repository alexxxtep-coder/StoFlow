# Модель безопасности

1. Сессия подтверждается `supabase.auth.getUser()` на сервере.
2. Активное членство выбирается из БД; роль из браузера не принимается.
3. Все tenant-таблицы имеют RLS; коммерческие/финансовые таблицы дополнительно ограничены ролями. Денежные поля вынесены из механик-facing строк работ.
4. Ключ Service Role не должен попадать в клиентский bundle.
5. Все Server Actions/Route Handlers обязаны валидировать входные данные и проверять tenant/permission.
6. Доступ к файлам — private bucket + tenant-scoped metadata + короткоживущие signed URLs.
7. Audit log фиксирует критические изменения.
8. Для production добавить rate limiting, MFA для владельцев, session revocation, security headers, secret rotation, dependency scanning и мониторинг.
9. Провести adversarial RLS tests: два tenant, роли, чтение/изменение/удаление, поиск, Storage, Realtime, экспорт.
10. Проверить законодательство Беларуси и условия размещения/трансграничной передачи персональных данных с профильным юристом.


## STO.Flow 6.0 дополнения (миграция 0002)

- Вставка/изменение рабочих ресурсов ограничена ролями owner, admin, service_manager.
- Просмотр списка memberships разрешён самому участнику, владельцу/администратору и руководителю сервиса; изменение состава команды отдельным интерфейсом пока не реализовано.
- Регистрация расходов ограничена owner, admin и finance.
- Атомарные RPC добавления строк заказ-наряда и регистрации/распределения платежей проверяют роль и принадлежность сущностей текущему tenant.


## Дополнительные финансовые инварианты (migration 0003)

- RPC платежа проверяет активную роль в tenant, клиента, соответствие клиента заказу, валюту организации, допустимый способ оплаты, точность до двух знаков и сумму не выше остатка.
- Строка заказ-наряда блокируется на время расчёта остатка; изменения строк/цен также сериализуются блокировкой родительского заказа.
- Триггер `payment_allocation_limit_guard` не допускает распределения больше суммы самого платежа или общей стоимости заказ-наряда, включая прямые записи через Supabase API.
- Проверка завершённого статуса выставляет `completed_at` на уровне PostgreSQL; дата завершения восстанавливается для старых заказов, если запись статуса сохранилась в истории.
- Эти правила прошли статический review, но требуют исполнения миграции и concurrency/RLS тестов на staging PostgreSQL до production.

- Migration 0003 hardens SECURITY DEFINER routines with fixed `pg_catalog, public, pg_temp` search paths and narrows execute grants.

## Дополнительные ограничения второго review

- Закрытые заказ-наряды (`completed`, `cancelled`) нельзя изменять через формы или прямые записи строк, финансовых значений, задач и заявок на детали.
- Изменение количества/цены не может уменьшить стоимость заказа ниже уже распределённых оплат; финансовые проверки выполняются с блокировкой родительского заказа.
- Строки заказа и финансовые значения нельзя перемещать между заказами/тенантами.
- Оплата отклоняется при отсутствии финансовой цены хотя бы у одной строки.
- `create_workspace` блокирует повторное/параллельное создание нескольких активных организаций одним пользователем, пока в приложении нет tenant switcher.
- Аналитика и карточка заказа не показывают нулевые финансовые значения ролям, у которых нет доступа к соответствующим данным.
- Даты хранятся как `timestamptz`, локальное время формы конвертируется с использованием IANA timezone организации; некорректный timezone не принимается настройками.
