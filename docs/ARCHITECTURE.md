# Архитектура

## Стек
Next.js App Router + React + TypeScript; Supabase Auth/PostgreSQL/Storage/Realtime; серверный DAL; Zod; Node tests/Vitest; Playwright.

## Слои
- `src/app`: маршруты, Server Components, Server Actions.
- `src/domain`: чистые доменные правила без инфраструктурных зависимостей.
- `src/lib/auth`: получение пользователя и активного членства.
- `src/lib/supabase`: серверный клиент Supabase.
- `supabase/migrations`: SQL schema, constraints, RLS, RPC.
- `integrations`: добавлять отдельными адаптерами после получения реальных credentials.
- `docs`: продуктовые и эксплуатационные решения.

## Источник истины
PostgreSQL. Realtime — доставка обновлений, не замена транзакций. Бизнес-правила, права и атомарные операции находятся на сервере/в БД.

## Multi-tenant
Каждая бизнес-таблица содержит tenant_id. Foreign keys `(entity_id, tenant_id)` запрещают связывать записи разных организаций. RLS проверяет активное членство пользователя.

## Критические операции
- Создание обращения с клиентом и автомобилем — одна SQL RPC-транзакция с дедупликацией по нормализованному телефону/VIN/госномеру.
- Изменение статуса заказа проверяется DB trigger и записывается в append-only history.
- Пересечение активных записей одного ресурса блокируется PostgreSQL exclusion constraint; live concurrency test ещё требуется.
- Платёж распределяется по заказам; сумма распределений не должна превышать доступный остаток платежа (следующий срез).
- Закупка и приёмка должны быть идемпотентны и журналироваться.

## Решение по HTML 5.7
Не переносить монолитный скрипт. Использовать HTML как UX-референс. Переписать бизнес-логику в domain/use-case слой, а UI — в небольшие компоненты.

## Дополнения второго quality review

- Все `datetime-local` значения трактуются как локальное время tenant timezone и конвертируются в UTC до записи; отображение использует тот же IANA timezone. SQL DATE остаётся date-only и не проходит через timezone conversion.
- Завершённые и отменённые заказ-наряды являются read-only для строк, цен, новых задач и заявок на детали. Ограничение продублировано на уровне PostgreSQL.
- Платёжные распределения сериализуются по родительскому заказу; изменение количества/цены не может уменьшить начисление ниже уже распределённой суммы.
- Создание tenant блокируется для пользователя с активным членством, пока multi-tenant switcher не реализован.
