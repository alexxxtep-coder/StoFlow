# STO.Flow 6.0 — повторный quality review (2026-11-19)

## Область проверки

Повторно просмотрены серверные действия, страницы, доменные функции, маршруты, связи с PostgreSQL, ролевые проверки, миграции 0001–0003 и цепочки данных: обращение → заказ → строки → снабжение → задача → оплата → архив/финансы.

## Подтверждённые проблемы, исправленные во втором проходе

1. **Часовые пояса.** Поля `datetime-local` интерпретировались временем серверной среды, а не timezone организации; даты отображались с локальной timezone сервера. Добавлен общий модуль `src/domain/timezone.mjs`: преобразование локального времени в UTC по IANA timezone, генерация значений для форм и форматирование дат. Календарь, задачи, архив, CRM, заказ, снабжение, верхняя панель и часть финансовых экранов теперь используют timezone организации.
2. **Невалидный timezone.** Настройки принимали произвольную строку. Сохранение теперь проверяет реальный IANA timezone.
3. **Изменение завершённого заказа.** В карточке завершённого/отменённого заказа ранее оставались формы добавления строк и задач. UI и серверные действия теперь блокируют это. Миграция 0003 добавляет DB-level guards для строк, финансовых значений, задач и заявок на детали, чтобы прямые запросы к таблицам не обходили правило.
4. **Финансовая целостность после оплаты.** Изменение количества/цены строки могло уменьшить сумму заказа ниже уже распределённых оплат. Добавлены блокировки родительского заказа, запрет перемещения строк между заказами/тенантами и триггер проверки `allocated_total <= billed_total` после изменения количества/цены.
5. **Неполные цены.** RPC распределения оплаты ранее трактовала отсутствующую финансовую запись как нулевую цену. Теперь операция отклоняется, если хотя бы у одной строки отсутствует финансовая запись.
6. **Точность чисел.** Добавлена проверка: суммы и цены — максимум 2 знака после запятой, количества работ/деталей — максимум 3. RPC строк заказ-наряда также проверяет точность и терминальный статус заказа до записи.
7. **Повторное создание организации.** RPC `create_workspace` ранее позволяла одному пользователю создать несколько активных рабочих пространств, хотя переключателя организации нет. Добавлена проверка активного членства и advisory transaction lock, предотвращающий параллельное двойное создание.
8. **Ролевые интерфейсы.** Снабжение теперь показывает создание заявки только ролям, разрешённым RLS. Карточка заказа не запрашивает распределения оплат для роли Parts Manager, у которой нет соответствующего SELECT-права. Аналитика теперь выполняет финансовые запросы и показывает суммы только ролям с соответствующими правами; недоступные суммы не маскируются нулями.

## Ранее исправленные проблемы, сохранённые в этой версии

- Реестр завершённых заказов в финансах и возможность распределить оплату на завершённый заказ.
- Проверка остатка заказа, валюты, метода и точности оплаты; блокировка превышения суммы платежа/заказа.
- Согласованность переходов статуса в UI, серверном действии и DB trigger.
- Раздельные права на чтение/создание расходов.
- RPC `create_lead_with_context` пересоздаётся после удаления старой сигнатуры, чтобы избежать ошибки PostgreSQL при изменении имен аргументов.
- Укреплены `SECURITY DEFINER` функции: фиксированный `search_path` и минимальные execute grants.
- Нормализация формы PostgREST для relation `tenants` в контексте членства.

## Что по-прежнему не доказано

- Установка зависимостей в этом контейнере не завершилась из-за недоступности npm registry/таймаута; `node_modules` отсутствует. Поэтому Next.js production build, ESLint и полноценный TypeScript semantic check не подтверждены.
- PostgreSQL/Supabase не подключены, `psql` недоступен. Миграции, RLS, triggers, RPC и транзакции не исполнялись на живой базе.
- Нет Playwright browser E2E, тестов параллельных бронирований/оплат на PostgreSQL, backup/restore, нагрузочного теста и независимого penetration test.
- GitHub repo не был доступен через подключённый аккаунт; изменения остаются в локальном архиве.

## Release gate

Это усиленная сборка для контролируемого staging/pilot теста, а не подтверждённая production-ready SaaS. Перед реальными данными: резервная копия, staging Supabase, миграции, multi-tenant/RLS тесты двумя организациями и несколькими ролями, затем браузерный сценарий end-to-end. Не применять SQL на production без staging rehearsal.
