## Граница проверки исходного кода
В текущем загруженном наборе есть исходный HTML 5.7, но нет самих HTML-файлов ранних поколений, которые перечислены в консолидированной спецификации. Поэтому кодовая проверка выполнена для 5.7; ранние поколения учтены по текстовому архиву/сводной спецификации, но их исходники повторно не инспектировались в этой сборке.

## Проверяемые наблюдения по HTML 5.7
- Заголовок документа: `STO.Flow 5.7 — Workshop Workflow & UX`.
- В HTML есть два встроенных JS-блока; один около 90 KB, второй около 467 KB.
- Интерфейс явно маркирует «Локальный режим» и говорит, что данные хранятся в браузере, серверная синхронизация не подключена.
- Есть переключение ролей: владелец, приёмщик, механик, снабжение. Это интерфейсное переключение, не доказательство авторизации.
- По видимому DOM — пять пунктов верхнего меню (Сегодня, Работа, Клиенты, Финансы, Управление); Снабжение расположено как контекст/внутри рабочих зон в этой версии.
- Встроенные функции/данные находятся в монолитных скриптах; проверенная версия не является модульным серверным приложением.
- Внешние API, облачная БД и серверная аутентификация не подтверждены самим HTML.

## Подтверждённая продуктовая логика
- Полный поток: обращение → клиент/авто → запись → заказ-наряд → детали/снабжение → ремонт → оплата → история/повторный визит.
- Шесть рабочих зон из консолидированной спецификации: Сегодня, Работа, Клиенты, Снабжение, Финансы, Управление.
- Parts.Finder — встроенный модуль снабжения и контекстный инструмент заказа, общая доменная модель.
- Операционный фокус первого сегмента — независимые небольшие и средние СТО Беларуси, ориентир 2–10 постов.
- BYN и `Europe/Minsk` — значения по умолчанию, настраиваемые организацией.
- Задача — отдельное действие в процессе, а не второй заказ-наряд.
- Финансы разделяют выручку/начисления, денежные поступления, прямые затраты, задолженность и валовую маржу.
- Ручной Parts.Finder — обязательный рабочий fallback; реальные API не имитируются.

## Презентации
Одностраничная PDF-презентация позиционирует продукт как единую систему управления СТО: порядок в заказах, контроль загрузки, понимание прибыли.
Коммерческая презентация содержит 13 слайдов: проблема разрозненных каналов, путь автомобиля, шесть рабочих пространств, панель владельца, единый заказ-наряд, календарь ресурсов, Parts.Finder, пример валовой прибыли, этапы исполнения, финансы, ролевые представления, честное разделение прототипа и production, пилотный следующий шаг.
Пример на слайде с экономикой условный: 200 BYN выручки, 137 BYN прямых затрат, 63 BYN ожидаемой валовой прибыли; это иллюстрация формулы, не прайс/реальная прибыль.

## Архитектурный вывод
Не переносить монолитный HTML в React одним компонентом. Использовать его как UX-референс и извлечь подтверждённые сценарии. Новая система должна строиться вокруг PostgreSQL, tenant isolation, серверных use cases, audit log и транзакционных правил.
